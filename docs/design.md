# design.md — シミュレーターの設計方針（2026-08-28 合意）

`docs/rules_confirmed.md` の確定情報に照らして盤面の作りを見直し、
カードデータの持ち方と作業の順序を決めたもの。
ここに書かれていることは **依頼者と合意済みの設計判断** であり、ルールの確定情報ではない。

---

## 1. 変えないもの

- ルールの判定・強制は実装しない。フェイズ送り、コスト支払い、バトル解決、ダメージ適用、
  エンドフェイズ処理はすべて人間が手で行う。シミュレーターは「場」と「表示」だけを提供する。
  **ただし能力欄の効果だけは例外として自動で処理する（2026-09-26 依頼者の指示。→ §2-2）。**
  **2026-10-04 依頼者の指示「ルールに則ってやって欲しい」により、確定しているルールのうち次の3つも自動にした（→ §2-4）:**
  引き直しは準備中に一度だけ／エンドフェイズのエナドローと使用済みのエナの戻し／オーバービートされたホロビトのダウン解除。
  **2026-10-12 依頼者の指示「今は作れるなら作れるところは作って欲しい／ルールに合わせて作るように」により、
  ラウンドの進行（準備・召喚フェイズの先手と後手・バトルフェイズ・エンドフェイズ）、コストの支払い、バトル、ダメージ、勝敗も
  確定している部分を自動にした（→ §2-4 §2-6）。** 未確定の部分は、これまでどおり聞くか手で処理してもらう。
- ハートゾーンは5枚を縦に重ね、あとのカードほど上に重ねて**持ち主に近い端**に置く（自分は下端、相手は上端。相手の列は逆向きに並べる）。
  ダメージは重なりの一番上から入る（ルール動画。2026-10-15）。
- 2陣地。中央で両者のバトルラインが向かい合う。iPhone では縦に積み、PC では上下に展開。
  **PC も iPhone も、公式の手引書の「盤面見本」どおりの1枚の盤にする**（依頼者の指示「盤面の並べ方はこう見たい」、2026-10-09）。
  自分は左にハートゾーン（縦に重ねる）、中央に上からライン→ワザ→エナ→手札、右に山札・墓地。相手は点対称。
  **ライン番号（第1〜第5ライン）は両者のバトルラインの間に1本だけ置き、両者で共有する。** その左右に「相手／自分」と先手・後手を出す。
  iPhone は同じ形のまま、カードと文字を小さくして幅に収める（カード 42×59px、左右の列 54px）。
  `#side-0` / `#side-1` は `display:contents` にして、中のゾーンを盤（`#board`）の格子に直接並べる。
- 1ラインは枚数無制限の配列。オーバービートの束をそのまま表現する。
- カードの向きは `turned` 1つで持つ（`rules_guess.md` A-1 の設計上の決定）。
- 単一 HTML。`simulator.html` が原本で、Artifact 用は `tools/build-artifact.mjs` で生成する。
- 素の JavaScript。TypeScript 化は見送り、データ側を JSON Schema で検証する（§4）。

## 2-2. 効果の自動処理（能力欄に限る）

依頼者の指示（2026-09-26）:
「自動で動く範囲は、発動するかどうかの可否の確認、ドローなどを行うこと、
対象の選択までプレイヤーを誘導すること」。

これは §1「ルールの判定・強制は実装しない」を**能力欄の効果に限って**変更するもの。
（2026-10-12 から、フェイズ・コスト・バトル・ダメージ・勝敗も確定している部分を自動にした。→ §2-4 §2-6）

`CLAUDE.md` の「推測はコードに入れない」は変えない。そのため:

- **確定情報で決まるものだけを自動で処理する。**
- **決まらないものは、シミュレーターが決めずにプレイヤーに聞く・選ばせる。**
  例: コストの比較は質問する（パワーは、2026-10-12 からバトルの中では計算する。§2-6）。（「正面」は 2026-10-09 に手引書で確定したので、相手の同じ番号のラインを自動で選ぶ）
- **推測で埋めるくらいなら、手で処理するよう案内して止める。**
  例: 捨てたカードの置き場所。（「回復する」は 2026-10-09 に手引書で定義が確定したので自動にした）
- 数え方が未確定のもの（束の下のカードを数えるか、色が未確定のカード）は、
  **考えられる数え方をすべて試し、結論が同じなら確定、割れたら聞く。**
- 同時に複数の効果が発動するときの順番は未確定なので、プレイヤーに選ばせる。
- ヘッダーの「効果: 自動／手動」で切り替えられる。手動にすると従来どおり何もしない。
- 自動処理の直前に Undo の区切りを入れる。「戻す」で効果だけを取り消せる。

**能力を持つカードは、画面の操作だけで効果を確かめる試験（`tests/cards-play.test.cjs`）に必ず入れる。**
盤面の初期配置だけをスクリプトで並べ、そこから先はカードのタップ・メニューのボタン・光ったカードのタップで進め、
印字から決めた期待値と比べる。入っていないカードがあると `npm test` が失敗する（`tools/check-play-coverage.mjs`）。
（2026-10-09: 依頼者の問い「効果通りの動きをしてるか確認した？」を受けて追加。それまで9枚が試験に一度も出てこず、
全カードを画面で動かしたところ「破壊されない」を無視して破壊するバグが見つかった）

部品ごとの扱いは `simulator.html` の `PART_FX` に1か所でまとめている。
**部品を辞書に足したのに `PART_FX` で扱いを決めていないと、`npm run build` が止まる。**

扱いの意味:

| 扱い | 意味 |
|---|---|
| 自動 | 盤面から判定・実行する |
| ボタン | バトル処理を作らないため、出来事はカードのメニューのボタンでプレイヤーが知らせる |

## 2-2b. ワザを使う

依頼者の指示（2026-10-04）:「ワザも自動で動くようにして」。2026-10-12 から、**バトルフェイズのバトルの中で使う**（§2-6）。
ブーストも 2026-10-15 から同じ手番で使える（ルール動画で使い方が確定した。§2-6）。
メニューの「このワザを使う」はなくした（バトルを扱うようになったので、使うホロビトを選ばせる必要がなくなった）。

| 手順 | 扱い | 根拠 |
|---|---|---|
| 1. 手札から使う | バトルのワザの手番で、手札のワザのうち、エナが足りるものを候補に出す | 確定（入門⑪「手札から使う」） |
| 2. 使うホロビト | そのラインでバトルしているホロビト（束の一番上） | 確定（手引書「バトル中のホロビトが使える」） |
| 3. 「〜ときのみ使える」の確認 | 「自分がこのバトルで他のワザを使っているときのみ」は、このバトルで自分が使ったワザを数えて判定する | 確定（印字） |
| 4. コストを払う | ワザと同じ色の未使用のエナで足りれば、それを自動で横向きにする。同じ色が足りなければ払うエナを選ばせる。未使用のエナ自体が足りなければ使えない（候補に出さない） | 確定（手引書②「必要なエナの色と数」、入門⑥）。**何枚がその色である必要があるかは未確定**（B-3）。同じ色だけで払えばどの決まりでも満たすので、そのときだけ自動 |
| 5. ワザの置き場所 | ワザゾーンに横向きで置く | 確定（手引書 盤面見本） |
| 6. 記録 | 使ったホロビトに「使ったワザ」を記録し、盤面に「ワザ+2000」の印を出す。パワーを比べるときに足す | 確定（手引書⑧ 左辺の `+N` がワザのパワー。ティザー⑫ 累積する） |
| 7. 発動 | ワザの「このワザを使ったとき」、使ったホロビトの「Nつ目のワザを使ったとき」を発動する | — |

## 2-8. デッキを作る画面（依頼者の指示 2026-10-16）

依頼者の指示:「こういうデッキを作るのが欲しいね」（参考に示されたのは、検索・デッキ・試遊のタブ、絞り込み、
カードの画像の一覧に −／枚数／＋ が付いた画面）。

| 画面（上部のボタン） | 出すもの |
|---|---|
| 🔍 カード | 自分／相手のどちらのデッキを組むかの切り替え。絞り込み（下の表）と「クリア」。カードの画像の一覧（iPhone は1行に4枚）。各カードに −／枚数／＋。画像をタップすると印字の全文と −／＋ のシート |
| 📋 デッキ | スタートデッキのタブ（§2-5）。合計枚数と未確定カードの枚数、種別ごと・色ごとの枚数、コスト別の枚数の棒。入っているカードの一覧（−／＋ 付き）。「このデッキで盤面を組み直す」 |
| 🎮 試遊 | これまでの盤面 |

絞り込みに使う項目は、`data/cards.json` に印字から写した項目だけにする。選択肢は起動時にカードデータにある値から作り、
読めない値（`unknown`）は「…: unknown（読めない）」という選択肢として選べるようにする（他の値に寄せない）。

| 絞り込み | 見る項目 |
|---|---|
| カード名・種族（文字） | `name`・`name_ruby`・`family` |
| 効果テキスト（文字） | `abilities` とトリガーの `keyword`・`text` |
| 種別・色・コスト | `type`・`color_mark`・`cost` |
| トリガー | `trigger.keyword` |
| 番号の記号 | `id` の「-」より前（HB01・HD02・PR など） |
| 絵師・レアリティ | `printings` の `illustrator`・`rarity_mark`（版のどれかが合えば出す） |
| 種族 | `family`（種族のないカード＝`null` は選択肢に出さない） |
| 並び | 番号順・コスト順・パワー順・名前順。読めない値は最後 |

- −／＋ は同名4枚（§2-1）と50枚を守る。押せないときはボタンを押せなくする。
- デッキを変えても盤面はすぐには変えない（遊んでいる途中の盤面を消さないため）。「🎮 試遊」で配るか、「📋 デッキ」の組み直しで反映する。
- どの画面を開いているか・どちらのデッキを組んでいるか・絞り込みは、表示の設定として端末に保存する（`horobeat-sim-ui`）。
  盤面の保存（`horobeat-sim-v2`）とは分け、「戻す」の対象にしない。デッキの枚数の変更は「戻す」で取り消せる。
- シートの −／＋ は、シートを開いたまま中身だけ書き換える（開き直すと誤タップ防止の待ちが入り、続けて押した分が消えるため）。
- 盤面にあるその陣地のカードが、いまのデッキの登録と違うときは、デッキの画面に「盤面は、まだ前のデッキのままです」と出す。
- 効果のログと「選ぶ」の案内は盤面のものなので、カード・デッキの画面では出さない（画面の下を覆って「組み直す」を押せなくしていた）。
- **確認はすべて画面の中のシートで聞く**（組み直す・盤面があるときの配り直し・バトルの途中のフェイズ送り）。
  公開先（アーティファクト）の画面ではブラウザの確認窓（`confirm`・`alert`・`prompt`）が出ず、`confirm` は押さずに「いいえ」になるため
  （2026-10-19 依頼者の報告「スターターを選択しても何も出ない」の原因）。試験は、確認窓が出たら失敗にし、ソースに使っていないことも確かめる。

## 2-9. 相手を AI にする（依頼者の指示 2026-10-22）

依頼者の指示:「AIが対戦相手にしてくれるようにできる」。作り方を2通り示し、依頼者が**シミュレーター内蔵のAI**を選んだ
（もう1つは、公開先の画面から Claude に1手ずつ聞く方法。手元のファイルでは動かず、1手ごとに時間と利用枠がかかる）。

- 上部の「相手: …」を押して「人／AI ふつう／AI かんたん」から選ぶ。AI が動かすのは「相手」の側だけ。この端末の表示の設定
  （`horobeat-sim-ui` の `ai` = `"normal"`／`"easy"`／`false`。以前の保存の `true` は `"normal"` として読む）で、盤面の「戻す」には含めない。
- **AI は人の手札の中身を見ない**（見るのは盤面・ハートの枚数と向き・手札とエナの枚数だけ。実際の対戦で相手から見えるもの）。
- **AI の手札は伏せて表示する**（既定。相手を選ぶシートで「見せる」にもできる。`horobeat-sim-ui` の `aiHide`）。表示だけを伏せ、カードの向き（`state`）は
  変えない。伏せたカードはタップしても中身を出さず、動かせない。勝敗が決まったら見せる（依頼者の指示 2026-10-22）。
- **AI が決めるのは、プレイヤーが自分で選ぶことだけ。** ルールが未確定でシミュレーターが聞くこと（束の下のカードの扱い、勝ったときの効果とダメージの順番、
  エナの色の決まり、条件を満たしているか など。`rules_guess.md`）は、**AI の番でも人に聞く**。AI にルールを推測させない（CLAUDE.md 原則3）。
- AI は、シミュレーターが「出せる・使える」と判定したものの中からだけ選ぶ（反則はしない）。次の出し方は人に聞くことになるので、AI は選ばない:
  同じ色のエナだけでは払えない（色の決まりが未確定。B-3）／下のホロビトの「コストは大きくなる」しだい（B-8）／コストが印字から読めない。
- AI は少し待ってから（既定 0.7 秒）1手ずつ動き、何をしたかを「相手（AI）：…」と記録に残す。AI の番の間は記録を消さない。
- AI の召喚フェイズの間は「フェイズ送り」を押せない。AI は自分の召喚フェイズを終えるとフェイズを送る（後手ならバトルフェイズに入る）。
  バトルフェイズ・エンドフェイズの「フェイズ送り」とバトルの結果の「続ける」は人が押す。
- 「戻す」で AI の番に戻ったときは AI を止め、上部に「AIを進める」を出す（止めている間は「フェイズ送り」も押せる）。

強さは2つ（2026-10-22 依頼者の選択「3です」= トークンを使わずに内蔵のAIを強くする）。

- **かんたん**: その場でいちばん伸びる出し方（下の表）。
- **ふつう**: 見えるものだけで、いまの盤面のままバトルしたら第1ラインから順に何が起きるかを数え、点数にして比べる（`aiForecast`）。
  数えるのは確定ルールだけ: 同じ番号のラインが正面／パワーの高いほうが勝ち／負けたホロビトとそのプレイヤーのハートにダメージ／
  引き分けはお互いのホロビトだけ／不戦勝も勝ち／ダウンしていればダメージで破壊／ハートは上から順に／ハートが0枚のときのダメージでトドメ／
  ダブルダメージ・バリア（判定できるときだけ）／エンドフェイズのエナドロー（未使用のエナの枚数分引く）。まだ使っていないワザ・ブーストは見通しに入れない。
  カードの効果（出たとき・バトルに勝ったとき・ダウンしたとき・バトルが終わったとき・オーバービートされるとき の、引く・捨てさせる・破壊する・
  手札に戻す・回復する・未使用にする）は、条件を判定できれば数え、判定できなければ半分に見る（`aiFxVal`）。
  点数の重み（`AI_W`）: ハートへのダメージ1回 10、トドメ 1000、ホロビトのダウン 1、破壊 4＋コスト×0.5、盤面に残るホロビト 0.5×(1＋パワー/2000)、
  カード1枚 2（`draw`。エナを1枚使うと、エンドフェイズのエナドローで1枚引けなくなるので、エナ1枚もこの値で数える）、使うカード 2（`card`）。
  - 出し方: 仮に置いてみて数え、すぐ元に戻す（`aiTry`）。点数の伸び（出たときの効果、下になるホロビトの「オーバービートされるとき」の効果を含む）から、
    使うエナ×2 を引いて、いちばん伸びる出し方。伸びなければ出さない。
    自分が先手の召喚フェイズでは、相手がこのあと出せるので、相手が空いているラインの不戦勝は半分に見る。
  - ワザ・ブースト: 上回っていれば使わない。手札のワザ・ブーストを、いまのラインとこのあとのライン（両方にホロビトがいるライン）にどう配るかを
    全部試し（`aiPlanBattle`。6枚まで）、見通しの点数から使うカード×2 とエナ×2 を引いていちばんよい配り方で、いまのラインに使うものを使う
    （負け→引き分けでハートへのダメージを防ぐ使い方も含む）。相手が返してくるワザは数えない（手札の中身は見ない）。
  - トリガーでラインに出す・オーバービートの下にするホロビト: このあとのバトル（まだバトルしていないライン）を見通していちばんよいもの。
- **強さの測り方**: `npm run ai:bench`（`tools/ai-bench.cjs`）。AI どうしを、側・スタートデッキ・先手を順に入れ替えて対戦させ、勝率を数える。
  ブラウザを3つ同時に動かす（`AI_WORKERS`）。`AI_WA`／`AI_WB` で側ごとに重みを変えられるので、「ふつう」どうしで改良の前後を直接比べられる。
  重みは `npm run ai:tune`（`tools/ai-tune.cjs`）で探す: 重みを1つだけ半分・倍にした挑戦者といまの重みを 600 局ずつ対戦させ、
  挑戦者の勝率の 95% の幅の下の端が 50% を超えたときだけ乗り換える。

## 2-11. 対戦の記録を見返す（依頼者の指示 2026-10-22）

## 2-1. 設計原則: 確定ルールが指定する「単位」でコードを書く

ルールを実装しない方針であっても、**確定ルールを反映する箇所では、
そのルールが指定している単位でコードを書く。**

実例（2026-09-18）:
デッキ構築の上限を **カード番号ごと** に数えていたため、
同名で番号違いのカード（しなずいさま = `HB01-034` / `HD02-001`）を
合計8枚入れられる状態になっていた。
確定情報は「同じ**名前**のカードは4枚まで」（ティザー②）であり、
番号ではなく名前が単位である。名前基準に修正した。

この原則の効き目は、**未確定の解釈から実装を切り離せる**ことにある。
「この2枚は同一カードの別仕様か」（→ `rules_guess.md` A-18）は未確定だが、
名前で数えている限り、どちらであっても結果は変わらない。
単位を取り違えると、未確定の解釈に実装が依存してしまう。

## 3. データ構造

### 3-1. カード実体（盤面上の1枚）

```
{ uid, key, up, turned, note }
```

- `uid`: 実体の識別子（`A-01` 等。所有元の識別を兼ねる）
- `key`: `data/cards.json` のカードの `key`。**未確定カードは `null`**
- `up`: 表向きか
- `turned`: 横向きか
- `note`: 自由文メモ（`""` が既定）

### 3-2. 陣地

```
players[2] × { heart[], line[5][], waza[], ena[], hand[], deck[], grave[], decklist }
```

`decklist` は `{ key: 枚数 }`。デッキを組み直すときに参照する。
進行のために、陣地に `redrawn`（引き直した）・`mull`（準備④の答え）・`enaCharged`（このラウンドのエナチャージ済み）・
`mainStarted`（このラウンドにホロビトを出した）を持つ。盤面全体には `phase`（-1 が準備、0〜3 が4つのフェイズ）・`first`・
`prep`・`battle`（バトルの進み具合）・`nextFirst`・`winner` を持つ。保存の形が変わったので `v: 3` を付け、
以前の保存（フェイズが3つ）は読み込むときにフェイズの番号を合わせる。

### 3-3. デッキ

50枚固定（確定）。`decklist` の登録カードを枚数ぶん並べ、
**残りを `key: null` の未確定カードで埋める**。
公開済みのカードだけでは50枚の実デッキが組めないため、無いものを捏造せず空席を空席として見せる。
同名は4枚まで（確定）。これだけはデッキ編集で守らせる。

## 4. カードデータの形式

### 4-1. 原則

- `data/cards.json` は **印字の写し** である。要約・言い換え・補完をしない。
- 印字されていない項目名は使わない（`color_mark`, `left_edge` という中立な名前にする）。
- `null` と `"unknown"` を厳密に分ける。
  カード全体が鮮明に見えていて何も印字されていない → `null`。読めない → `"unknown"`。
- 効果（`abilities`）は ● 1つにつき文字列1つ、印字どおり。**解釈を混ぜない。**
- `keywords` のような抽出欄は作らない。条件付きで「得る」キーワードを
  「持っている」ように見せてしまうため。
- 出典と判読の確度は **版（printing）ごと** に付ける。同じ番号でも版が違えば別の出典。
- 形式は `data/cards.schema.json` で強制し、`tools/validate-cards.mjs` を通らないデータは埋め込まない。

### 4-2. 1枚の形

```json
{
  "key": "HB01-049",
  "id": "HB01-049",
  "type": "ホロビト",
  "name": "ふわふわイロハとぶかぶかジャンボ",
  "name_ruby": "unknown",
  "color_mark": "緑",
  "cost": 5,
  "power": 6000,
  "family": "unknown",
  "left_edge": null,
  "abilities": [
    "自分の第1〜2ラインにいるホロビトの下にあるカードの合計が3枚以上なら、このホロビトのパワーを+3000し、ダブルダメージを得る。（ダブルダメージを持つホロビトがバトルに勝ったなら、相手プレイヤーに1ではなく2ダメージを与える）"
  ],
  "flavor": null,
  "trigger": { "icon": "上", "keyword": "オーバーT", "text": "このホロビトをオーバービートで出す。（コストは支払わない）" },
  "printings": [
    { "rarity_mark": "DR", "illustrator": "tomy", "frame": "縦札",
      "source": "イベント実物写真", "source_date": "unknown", "legibility": "partial" }
  ],
  "notes": ["ファミリー名はカタカナ表記だが判読不能"]
}
```

- `key` は検索用の識別子。通常は `id` と同じ。**カード番号が読めないカードは
  `id: "unknown"` とし、`key` に `UNKNOWN-` で始まる仮の値を付ける。**
- `left_edge` は `null`（印字なし）／`"unknown"`（何かあるが読めない）／
  `{ "modifier": "+2000", "cost": 1 }` のいずれか。`cost` は丸数字がなければ `null`。
- `printings[]` は1件以上。`legibility` は `high`（高解像度画像）／`partial`（一部判読不能）。
- `flavor` は能力欄の下の文章の欄（**フレーバー**）の印字をそのまま入れる。
  話者や出典（`―理系インテ` / `―『滅徒大全』〜第三巻 獣の項〜`）も印字どおりに含め、
  2つ並んでいる場合は改行で区切る。**印字がなければ `null`、読めなければ `"unknown"`。**
  フレーバーに書かれている内容がルールの説明に読める場合（PR-013 など）も、
  解釈せず印字どおりに置く。

### 4-2b. 数えれば分かることは数えて出す

カード番号の一覧、ファミリーごとの枚数、能力欄が空のカードの一覧——
こうした台帳を `rules_confirmed.md` に手で書くと、カードが増えるたびに壊れる。
実際に「能力欄が空のカード」を3枚数え落とし、『滅徒大全』の初例を取り違えた。

`data/cards.json` から出せるものは、ツールで生成して doc に差し込む。

| 生成するもの | ツール | 差し込み先 |
|---|---|---|
| 能力文の部品と使用カード | `tools/ability.mjs index` | `rules_confirmed.md` §11-4 |
| カードごとの能力文の分解 | `tools/ability.mjs build` | `data/abilities.json` |
| カードデータの集計 | `tools/card-index.mjs` | `rules_confirmed.md` §14-3 |

すべて `npm run build` に入っている。マーカー
（`@@ABILITY_INDEX_BEGIN@@` / `@@CARD_INDEX_BEGIN@@`）の内側は手で書かない。

**生成物に解釈を入れない。** 索引が並べているのは印字された文字列と、
その出現枚数だけである。「これはこういう意味だ」は
`rules_guess.md` に書く。

### 4-2c. 能力文の部品化

能力文を「発火条件1 / 発火条件2 / 効果条件 / 効果 / 制限 / 補足 / キーワード」の
部品に分け、部品に値を入れれば文を組み立てられるようにしている。

```
このホロビトが出たとき、下にカードがないなら、カードを1枚引く。
└発火条件1─┘ └発火条件2┘ └──効果条件──┘  └─効果(n=1)─┘
this_holobito  entered     no_cards_under   draw{n:1}
```

| ファイル | 中身 | 誰が書くか |
|---|---|---|
| `data/ability-parts.json` | 部品の辞書（役割・文面テンプレート） | 人が書く |
| `data/abilities.json` | カードごとの分解結果 | `tools/ability.mjs build` が生成 |
| `data/cards.json` の `abilities` | 印字そのもの | 人が書く（**正はこちら**） |

効果が「。」で終わったあと、次の文の頭に条件が来ることがある。
その条件はその効果の `if` に入る（例: 「…見せてもよい。**そうしたなら、**カードを1枚引く。」→
`draw` の `if` に `did_so`）。

**守っている約束:**

1. **印字が正。** 分解は `cards.json` の印字から機械的に作る。逆向きはない。
2. **往復一致。** 部品から組み立て直した文が印字と1文字でも違えば、その分解は採用しない。
   正規表現が緩くても、印字にない文字が紛れ込むことはない。
3. **自由な引数は区切りをまたがない。** `{target}` などは「、。（）改行」を含めない。
   含めると節ごと飲み込んでも往復一致してしまうため（実際に起きた）。
   候補が複数あるときは、部品の文面で説明できる文字が最も多いものを採る。
4. **部品は印字からしか作らない。** どのカードにも使われていない部品は検証で弾かれる。
5. **組み立てた文は候補でしかない。** 値を変えて作った文（「カードを2枚引く」等）は、
   新しいカードの印字と照合して一致したときだけ正とする。
6. **役割名はルール用語ではない。** 「とき」と「なら」の処理上の違いなどは `unknown`。

**カードを追加するとき:** `cards.json` に印字を入れて `npm run build`。
既存の部品で組み立てられれば自動で分解される。できなければ、
どこまで読めてどの役割の部品が足りないかが表示されるので、
その部品を `ability-parts.json` に足す（印字から切り出す）。

### 4-3. 解釈は別ファイル

§4-2c の部品化は**文面の構造**であって、処理の意味ではない。
ルールエンジンを作る段になったら、処理の意味（いつ・誰が・何を）は `data/effects_interpreted.json` に置く。
`cards.json` には入れない。`rules_confirmed.md` と `rules_guess.md` の関係と同じ。
**当面シミュレーターは `cards.json` しか読まない。** 効果は表示するだけで、適用は人間が行う。

```
simulator.html            原本。cards.json を所定ブロックに埋め込んで単体で動く
data/cards.json           印字レコード（正本）
data/cards.schema.json    形式の強制
tools/validate-cards.mjs  検証。通らなければ埋め込まない
tools/build-cards.mjs     cards.json を simulator.html の @@CARDS@@ ブロックへ埋め込む
tools/build-artifact.mjs  Artifact 公開用 HTML の生成
tools/crop-card.py        告知バナーからカード領域を切り出す（読み取り用）
```

## 5-1. 告知バナーからの切り出し

1920x1080 の告知バナーをそのまま読むと、カード内の小さな文字（能力文・カード番号）が
実効解像度で潰れる。カード領域だけを切り出して拡大すると、**同じ元画像から読める文字が増える**。

```
python3 tools/crop-card.py IN.jpg OUT.png --scale 1.6 --pad 4   # 自動検出
python3 tools/crop-card.py IN.jpg OUT.png --box 244,116,624,848 # 手動指定
```

自動検出は「細かい絵柄が密な領域のうち、縦横比がカードらしいもの」を選ぶ。
レイアウトが変わると外すため、**出力画像を必ず目視で確認してから読む**。
外したときは `--box` で指定し直す。

読み取り精度そのものが上がるわけではない。読める画素数が増えるだけであり、
それでも読めない箇所は従来どおり `unknown` とする。
