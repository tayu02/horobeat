# design.md — シミュレーターの設計方針（2026-08-28 合意）

`docs/rules_confirmed.md` の確定情報に照らして盤面の作りを見直し、
カードデータの持ち方と作業の順序を決めたもの。
ここに書かれていることは **依頼者と合意済みの設計判断** であり、ルールの確定情報ではない。

---

## 1. 変えないもの

- ルールの判定・強制は実装しない。フェイズ送り、コスト支払い、バトル解決、ダメージ適用、
  エンドフェイズ処理はすべて人間が手で行う。シミュレーターは「場」と「表示」だけを提供する。
- 2陣地。中央で両者のバトルラインが向かい合う。iPhone では縦に積み、PC では上下に展開。
- 1ラインは枚数無制限の配列。オーバービートの束をそのまま表現する。
- カードの向きは `turned` 1つで持つ（`rules_guess.md` A-1 の設計上の決定）。
- 単一 HTML。`simulator.html` が原本で、Artifact 用は `tools/build-artifact.mjs` で生成する。
- 素の JavaScript。TypeScript 化は見送り、データ側を JSON Schema で検証する（§4）。

## 2. 直すもの（確定情報が根拠）

| 変更 | 根拠 | 内容 |
|---|---|---|
| ラインの束に枚数バッジ | HB01-049「下にあるカードの合計が3枚以上」 | 2枚以上重なったラインに「N枚」を表示。数えるのは人間 |
| エナのまとめ操作 | 入門⑥「コスト分のエナを使用済みに」、コスト9・10のカード | エナゾーンの見出しをタップ→「未使用をN枚横向き（左から）」「全て縦向きに戻す」。人間が押すボタンで、フェイズには連動しない |
| 実カードの表示 | §12 印字項目、§14-1 色 | ダミーカードを `data/cards.json` の実カードに置き換える。色・コスト・パワー・名前を表示 |
| タップ時に印字テキスト全文 | 全カードにトリガー、複数の能力文 | メニュー上部に印字内容をそのまま出す。読んで適用するのは人間 |
| カードのメモ | HB01-049「ダブルダメージを得る」、ワザの累積 | 自由文のメモをカード実体に付ける。「+3000」「ダブルダメージ」など |
| 山札から N 枚引く | エナドロー | 枚数は人間が指定 |
| 端末への保存 | 運用上の要求 | 盤面とデッキ構成を localStorage に保存。ルールとは無関係 |

**やらないこと**: 上記のどれも自動実行しない。「全て縦向きに戻す」はボタンであり、
エンドフェイズに紐づけない。

## 2-1. 設計原則: 確定ルールが指定する「単位」でコードを書く

ルールを実装しない方針であっても、**確定ルールを反映する箇所では、
そのルールが指定している単位でコードを書く。**

実例（2026-09-18）:
デッキ構築の上限を **カード番号ごと** に数えていたため、
同名で番号違いのカード（しなずいさま = `HB01-034` / `HD02-001`）を
合計8枚入れられる状態になっていた。
確定情報は「同じ**名前**のカードは4枚まで」（ティザー②）であり、
番号ではなく名前が単位である。名前基準に修正した。

この原則の効き目は、**未確定の解釈から実装を切り離せる**ことにある。
「この2枚は同一カードの別仕様か」（→ `rules_guess.md` A-18）は未確定だが、
名前で数えている限り、どちらであっても結果は変わらない。
単位を取り違えると、未確定の解釈に実装が依存してしまう。

## 3. データ構造

### 3-1. カード実体（盤面上の1枚）

```
{ uid, key, up, turned, note }
```

- `uid`: 実体の識別子（`A-01` 等。所有元の識別を兼ねる）
- `key`: `data/cards.json` のカードの `key`。**未確定カードは `null`**
- `up`: 表向きか
- `turned`: 横向きか
- `note`: 自由文メモ（`""` が既定）

### 3-2. 陣地

```
players[2] × { heart[], line[5][], waza[], ena[], hand[], deck[], grave[], decklist }
```

`decklist` は `{ key: 枚数 }`。デッキを組み直すときに参照する。

### 3-3. デッキ

50枚固定（確定）。`decklist` の登録カードを枚数ぶん並べ、
**残りを `key: null` の未確定カードで埋める**。
公開済みのカードだけでは50枚の実デッキが組めないため、無いものを捏造せず空席を空席として見せる。
同名は4枚まで（確定）。これだけはデッキ編集で守らせる。

## 4. カードデータの形式

### 4-1. 原則

- `data/cards.json` は **印字の写し** である。要約・言い換え・補完をしない。
- 印字されていない項目名は使わない（`color_mark`, `left_edge` という中立な名前にする）。
- `null` と `"unknown"` を厳密に分ける。
  カード全体が鮮明に見えていて何も印字されていない → `null`。読めない → `"unknown"`。
- 効果（`abilities`）は ● 1つにつき文字列1つ、印字どおり。**解釈を混ぜない。**
- `keywords` のような抽出欄は作らない。条件付きで「得る」キーワードを
  「持っている」ように見せてしまうため。
- 出典と判読の確度は **版（printing）ごと** に付ける。同じ番号でも版が違えば別の出典。
- 形式は `data/cards.schema.json` で強制し、`tools/validate-cards.mjs` を通らないデータは埋め込まない。

### 4-2. 1枚の形

```json
{
  "key": "HB01-049",
  "id": "HB01-049",
  "type": "ホロビト",
  "name": "ふわふわイロハとぶかぶかジャンボ",
  "name_ruby": "unknown",
  "color_mark": "緑",
  "cost": 5,
  "power": 6000,
  "family": "unknown",
  "left_edge": null,
  "abilities": [
    "自分の第1〜2ラインにいるホロビトの下にあるカードの合計が3枚以上なら、このホロビトのパワーを+3000し、ダブルダメージを得る。（ダブルダメージを持つホロビトがバトルに勝ったなら、相手プレイヤーに1ではなく2ダメージを与える）"
  ],
  "flavor": null,
  "trigger": { "icon": "上", "keyword": "オーバーT", "text": "このホロビトをオーバービートで出す。（コストは支払わない）" },
  "printings": [
    { "rarity_mark": "DR", "illustrator": "tomy", "frame": "縦札",
      "source": "イベント実物写真", "source_date": "unknown", "legibility": "partial" }
  ],
  "notes": ["ファミリー名はカタカナ表記だが判読不能"]
}
```

- `key` は検索用の識別子。通常は `id` と同じ。**カード番号が読めないカードは
  `id: "unknown"` とし、`key` に `UNKNOWN-` で始まる仮の値を付ける。**
- `left_edge` は `null`（印字なし）／`"unknown"`（何かあるが読めない）／
  `{ "modifier": "+2000", "cost": 1 }` のいずれか。`cost` は丸数字がなければ `null`。
- `printings[]` は1件以上。`legibility` は `high`（高解像度画像）／`partial`（一部判読不能）。
- `flavor` は能力欄の下の文章の欄（**フレーバー**）の印字をそのまま入れる。
  話者や出典（`―理系インテ` / `―『滅徒大全』〜第三巻 獣の項〜`）も印字どおりに含め、
  2つ並んでいる場合は改行で区切る。**印字がなければ `null`、読めなければ `"unknown"`。**
  フレーバーに書かれている内容がルールの説明に読める場合（PR-013 など）も、
  解釈せず印字どおりに置く。

### 4-2b. 数えれば分かることは数えて出す

カード番号の一覧、ファミリーごとの枚数、能力欄が空のカードの一覧——
こうした台帳を `rules_confirmed.md` に手で書くと、カードが増えるたびに壊れる。
実際に「能力欄が空のカード」を3枚数え落とし、『滅徒大全』の初例を取り違えた。

`data/cards.json` から出せるものは、ツールで生成して doc に差し込む。

| 生成するもの | ツール | 差し込み先 |
|---|---|---|
| 能力文の部品と使用カード | `tools/ability.mjs index` | `rules_confirmed.md` §11-4 |
| カードごとの能力文の分解 | `tools/ability.mjs build` | `data/abilities.json` |
| カードデータの集計 | `tools/card-index.mjs` | `rules_confirmed.md` §14-3 |

すべて `npm run build` に入っている。マーカー
（`@@ABILITY_INDEX_BEGIN@@` / `@@CARD_INDEX_BEGIN@@`）の内側は手で書かない。

**生成物に解釈を入れない。** 索引が並べているのは印字された文字列と、
その出現枚数だけである。「これはこういう意味だ」は
`rules_guess.md` に書く。

### 4-2c. 能力文の部品化

能力文を「発火条件1 / 発火条件2 / 効果条件 / 効果 / 制限 / 補足 / キーワード」の
部品に分け、部品に値を入れれば文を組み立てられるようにしている。

```
このホロビトが出たとき、下にカードがないなら、カードを1枚引く。
└発火条件1─┘ └発火条件2┘ └──効果条件──┘  └─効果(n=1)─┘
this_holobito  entered     no_cards_under   draw{n:1}
```

| ファイル | 中身 | 誰が書くか |
|---|---|---|
| `data/ability-parts.json` | 部品の辞書（役割・文面テンプレート） | 人が書く |
| `data/abilities.json` | カードごとの分解結果 | `tools/ability.mjs build` が生成 |
| `data/cards.json` の `abilities` | 印字そのもの | 人が書く（**正はこちら**） |

**守っている約束:**

1. **印字が正。** 分解は `cards.json` の印字から機械的に作る。逆向きはない。
2. **往復一致。** 部品から組み立て直した文が印字と1文字でも違えば、その分解は採用しない。
   正規表現が緩くても、印字にない文字が紛れ込むことはない。
3. **自由な引数は区切りをまたがない。** `{target}` などは「、。（）改行」を含めない。
   含めると節ごと飲み込んでも往復一致してしまうため（実際に起きた）。
   候補が複数あるときは、部品の文面で説明できる文字が最も多いものを採る。
4. **部品は印字からしか作らない。** どのカードにも使われていない部品は検証で弾かれる。
5. **組み立てた文は候補でしかない。** 値を変えて作った文（「カードを2枚引く」等）は、
   新しいカードの印字と照合して一致したときだけ正とする。
6. **役割名はルール用語ではない。** 「とき」と「なら」の処理上の違いなどは `unknown`。

**カードを追加するとき:** `cards.json` に印字を入れて `npm run build`。
既存の部品で組み立てられれば自動で分解される。できなければ、
どこまで読めてどの役割の部品が足りないかが表示されるので、
その部品を `ability-parts.json` に足す（印字から切り出す）。

### 4-3. 解釈は別ファイル

§4-2c の部品化は**文面の構造**であって、処理の意味ではない。
ルールエンジンを作る段になったら、処理の意味（いつ・誰が・何を）は `data/effects_interpreted.json` に置く。
`cards.json` には入れない。`rules_confirmed.md` と `rules_guess.md` の関係と同じ。
**当面シミュレーターは `cards.json` しか読まない。** 効果は表示するだけで、適用は人間が行う。

## 5. ファイル構成

```
simulator.html            原本。cards.json を所定ブロックに埋め込んで単体で動く
data/cards.json           印字レコード（正本）
data/cards.schema.json    形式の強制
tools/validate-cards.mjs  検証。通らなければ埋め込まない
tools/build-cards.mjs     cards.json を simulator.html の @@CARDS@@ ブロックへ埋め込む
tools/build-artifact.mjs  Artifact 公開用 HTML の生成
tools/crop-card.py        告知バナーからカード領域を切り出す（読み取り用）
```

## 5-1. 告知バナーからの切り出し

1920x1080 の告知バナーをそのまま読むと、カード内の小さな文字（能力文・カード番号）が
実効解像度で潰れる。カード領域だけを切り出して拡大すると、**同じ元画像から読める文字が増える**。

```
python3 tools/crop-card.py IN.jpg OUT.png --scale 1.6 --pad 4   # 自動検出
python3 tools/crop-card.py IN.jpg OUT.png --box 244,116,624,848 # 手動指定
```

自動検出は「細かい絵柄が密な領域のうち、縦横比がカードらしいもの」を選ぶ。
レイアウトが変わると外すため、**出力画像を必ず目視で確認してから読む**。
外したときは `--box` で指定し直す。

読み取り精度そのものが上がるわけではない。読める画素数が増えるだけであり、
それでも読めない箇所は従来どおり `unknown` とする。

## 6. 作業の順序

1. `cards.json`・スキーマ・検証・埋め込み
2. カードの表示と、タップ時のテキスト全文
3. デッキ編集
4. 束の枚数バッジ、エナのまとめ操作、N枚引く
5. カードのメモ
6. 端末への保存
